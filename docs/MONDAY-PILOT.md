# 2026년 11월 2일(월) 회사 시험 사용

## 현재 준비와 남은 단계

개발 환경에서 기능·출력·은행 파일 가져오기 흐름을 검증했다. 이번에 운영 설정 검사, Render 배포 설정, 비밀정보를 노출하지 않는 상태 점검, DB 백업·별도 DB 복구 도구를 추가했다.

실제 인터넷 서버, 운영 DB, 접속 주소, 운영 비밀번호, 예약 백업은 아직 개설·설정되지 않았다. 이 Codex 개발 환경은 상시 업무용 서버가 아니다. 회사 접속은 아래 서버 개설과 배포 후 실제 주소에서 확인해야 한다. 월요일 사용은 그 확인 완료를 조건으로 한다.

## 사용자가 먼저 준비할 것

1. https://dashboard.render.com 에서 본인 계정으로 가입한다. GitHub 연결은 `chokiyeon/dongyang-erp` 저장소에 필요한 범위로 한다.
2. 서버와 DB는 유료 구성이다. 요금 화면에서 월 비용·지역·DB 백업 보존 기간을 확인하고 사용할 구성을 결정한다. 요금을 확정하거나 서버를 구매한 상태가 아니다.
3. 로그인 비밀번호는 서비스의 비밀 환경변수 화면에 직접 설정한다. 개발 환경의 비밀번호·세션 키·DB를 복사하지 않는다.

별도 도메인 구매 없이 제공되는 HTTPS 주소로 시험 사용할 수 있다. 회사 컴퓨터에서는 크롬 또는 엣지로 접속한다.

## 배포 작업 순서

- 검토한 현재 코드를 GitHub 저장소에 반영한다. 현재 개발 체크아웃의 코드를 Render가 자동으로 읽는 것은 아니다.
- 저장소의 `render.yaml`로 Blueprint를 생성한다. 설정은 웹 서버와 PostgreSQL 17, Singapore 지역의 유료 구성 예시다. 제공업체 화면에서 지원 여부·요금을 확인하고 최종 개설한다.
- `ERP_ADMIN_PASSWORD`는 운영 전용 16자 이상, `ERP_SESSION_SECRET`는 별도 무작위 32자 이상, `ERP_COOKIE_SECURE=true`를 사용한다. DB 주소는 플랫폼 내부 DB 연결로 주입한다. DB 외부 IP 허용은 기본 차단한다.
- 빌드 후 `deploy:prepare`가 운영 설정과 DB 마이그레이션을 확인한다. 시작 명령은 `start:cloud`, 점검 주소는 `/api/health`이다. 자동 재배포는 꺼 둔다.
- 실제 HTTPS 주소에서 로그인·저장·다시 열기·엑셀 다운로드·인쇄를 확인하고 회사 컴퓨터에서도 같은 주소로 접속한다.
- 운영 DB의 예약 백업과 보존 기간을 제공업체에서 실제로 설정·확인한다. 별도 복구 DB에 백업 복구를 확인한 후 실제 회사 자료를 등록한다.

## 월요일 처음 사용할 범위

기존 엑셀을 함께 유지하고 장부·현장별 지출을 먼저 시험한다.

1. 법인명·공동대표자를 등록한다.
2. 실제 계좌 별칭 8개를 등록한다: 하나 2, 기업 1, 전북 1, 국민 1, 우리 2, 신한 1. 확인된 마이너스 약정은 전북 200,000,000원(2026-11-02 재확인), 신한 50,000,000원이다. 계좌 잔액과 마이너스 사용액은 은행에서 직접 확인하며 약정 한도를 현금에 더하지 않는다.
3. 실제 진행 중인 현장 6~7개와 주요 거래처를 등록한다.
4. 한 계좌의 짧은 기간 은행 `.xlsx` 파일부터 가져온다. 날짜·입출금 합계·중복 여부를 원본과 비교한다. 현재 공통 열 인식 방식이므로 은행별 원본 양식은 현장 확인이 필요하다.
5. 거래 종류를 고르고, 현장을 확인한 지출만 자재비·인건비·기타비로 배분한다. 모르면 미분류·미배분으로 남긴다.
6. 저장 후 화면을 다시 열어 값이 유지되는지 확인하고 엑셀·인쇄 결과를 원본과 비교한다.

급여·노무 신고, 어음, 차량·재고, 법인세까지 기존 업무를 대체하는 전체 개통은 아니다. 부가세는 확인된 입력 증빙 기준의 자료 점검용 추정이다.

## 송금 준비 시험 순서

실제 이체 전 한 거래처·한 공사로 확인합니다. 거래처 계좌를 등록·확인하고 지급 조건을 다음 달 말일로 설정한 뒤, 9월 매입의 기한이 10월 31일인지 대조합니다. 월세·전기요금은 해당 지급월을 준비하고 기존 매입 또는 지출 예정과 연결합니다.

송금 준비표에서 기준일과 현장을 선택하고 이번 지급 대상만 체크합니다. 거래처 계좌별 합계와 공사별 상세를 원본과 비교한 다음 미리보기·프린트·엑셀 저장을 확인합니다. 일부 지급한 건은 잔액만 표시되어야 합니다.

실제 송금 후 각 항목의 지급 내역 연결에서 은행 출금을 반영하고 송금표를 다시 조회합니다. 출력만으로 지급 완료되지 않습니다. 같은 지급을 수기 실적과 은행 연결에 중복 입력하지 않습니다. [자세한 순서](TRANSFER-PREPARATION.md).

## 인사·급여 시험 순서

한 명의 합성 직원과 시험 현장으로 직원·계약 단가 → 현장 출역·공수 → 월별 급여 검토 → 급여 지급 확인을 확인합니다. 실제 직원 자료를 대량 입력하기 전에 근로계약 일당과 공수·일당 계산액을 원본과 대조합니다. 신호수 계약은 일반 작업과 별도로 등록합니다. 월급제는 출역을 요구하지 않고 실지급액 산정 근거를 직접 확인합니다.

직원 수취계좌를 확인하고, 확정 실지급액을 송금표에서 조회·인쇄합니다. 실제 지급 후 은행 거래 연결과 잔액 갱신을 확인합니다. 실지급액만으로 세무 신고 금액이나 총 노무 원가를 확정하지 않습니다. [상세 사용법](LABOR-AND-PAYROLL.md).

## 백업과 복구 도구

PostgreSQL 17 클라이언트의 `pg_dump`, `pg_restore`가 필요하다. 운영 서버의 비밀 환경변수 또는 비공개 `.env`로 연결 정보를 제공한다.

```bash
npm run db:backup
# 파일은 backups/ 아래 생성, 기존 파일 덮어쓰기 금지, 권한 0600

# ERP_RESTORE_DATABASE_URL에 별도 빈 복구 DB 주소를 설정한 뒤
npm run db:restore -- /비공개경로/backup.dump
```

복구는 기존 업무 DB와 같은 주소 및 자료가 있는 대상 DB를 거절한다. 복구 완료 후 자료를 대조한 다음에 운영 연결을 전환한다. 실제 DB에서 곧바로 시험 복구하지 않는다. 백업 파일은 회사 자료 전체를 포함하므로 저장소·공개 다운로드 폴더에 올리지 않는다.

백업 도구가 있다는 것과 자동 백업이 실행 중이라는 것은 다르다. 정기 실행·별도 보관·복구 점검은 서버 개설 후 완료해야 한다.

## 원본·자사 이체·구두승인 추가 확인

첨부는 한 건의 합성 PDF/사진으로 연결·다운로드·취소·복원을 먼저 확인합니다. 회계 전달본의 ZIP을 열어 엑셀과 해당 원본이 함께 있는지 확인합니다. 기존 NAS 자료는 직접 수정하지 않습니다.

자사 계좌 간 같은 금액의 출금/입금을 선택해 이체 연결과 이체 제외 합계를 확인합니다. 실제 거래에 연결된 매입·현장 배분·예정이 있으면 해당 원본을 먼저 대조합니다. 원래 은행 금액·잔액이 보존되는지 확인합니다.

송금 준비표에서 검토본을 저장하고 실제 전달받은 구두승인의 대표자·날짜·내용을 기록합니다. 은행 실행·전자서명이 아닌 전달 기록입니다. 승인 후 금액·계좌가 바뀌면 새 검토본으로 확인합니다.

첨부 포함 백업에는 PostgreSQL 17 도구가 필요하며, Linux Docker DB를 사용하는 경우 ERP_PG_TOOLS_CONTAINER로 도구 컨테이너를 명시할 수 있습니다. 예약 백업과 별도 복구 점검은 운영 환경에서 실제 설정해야 합니다.
