# 동양계전 ERP

공사 원가와 회사 자금을 연결하는 웹 ERP. 개발·실행은 클라우드에서 수행하며 사용자는 브라우저로 접속합니다.

## 현재 상태

회사·현장·거래처·계좌 등록/수정, 관리자 로그인, 통합 은행 입출금 장부, 수기 입출금 예정과 실제 처리, 3/6개월 자금 전망을 구현했습니다.
통합 장부는 직접 등록과 공통 열 형식의 .xlsx 가져오기를 지원합니다. 은행별 실제 양식 추가 매핑과 급여 관리는 후속 개발 대상입니다. 예정·발행어음·수취어음의 은행 거래 연결과 할인 현금화를 지원합니다.
상세 범위와 계산의 한계는 [구현 상태](docs/IMPLEMENTATION.md)를 확인하세요.
실제 회사·계좌·급여 자료는 자동으로 생성하지 않습니다.

## 개발 시작

Node.js 24 LTS, npm, Docker Compose가 필요합니다. 회사 PC에 설치할 필요는 없습니다.
기존 클라우드 체크아웃을 사용하며 별도 작업 트리는 만들지 않습니다.

```bash
cd /workspace/dongyang-erp
# .env가 없을 때만 복사합니다. 운영에는 별도 비밀값이 필요합니다.
cp -n .env.example .env
npm ci
npm run access:local
npm run db:generate
docker compose up -d --wait db
npm run db:deploy
npm run dev -- --hostname 127.0.0.1
```

`access:local`은 로컬용 관리자 비밀번호·세션 키를 `.env`에 생성하며 값을 출력하지 않습니다.
기존 설정은 보존하고 파일 권한을 제한합니다. 외부 HTTPS 운영에서는 `ERP_COOKIE_SECURE=true`와 별도 자격증명을 설정해야 합니다.
실제 로그인에 사용할 비밀번호는 실행 환경의 `ERP_ADMIN_PASSWORD`에 안전하게 설정합니다(12자 이상).
`ERP_SESSION_SECRET`는 별도의 무작위 키 32자 이상이 필요합니다. 비밀값을 채팅·Git·테스트 로그에 넣지 마세요.
설정이 없으면 로그인과 업무 페이지 접근을 차단합니다. 개발용 자동 생성 비밀번호를 운영에 사용하지 않습니다.

개발 서버는 기본 3000번 포트입니다. 기존 `.env`와 DB 볼륨은 보존합니다.
`docker compose down`은 프로세스를 중지하지만 데이터 볼륨은 유지합니다.
`docker compose down -v`는 데이터를 삭제하므로 일반 종료에 사용하지 않습니다.

## 검증

```bash
npm run db:validate
npm run db:check
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
```

`db:check`는 Prisma 모델의 생성·조회·정밀 금액·미확인 한도·롤백을 확인합니다.
`npm test`의 DB 검증은 트랜잭션을 롤백합니다.
브라우저 검증은 시스템 Chromium(`/usr/bin/chromium`)을 사용하며 다른 위치는 `PLAYWRIGHT_CHROMIUM_PATH`로 지정합니다.
프로덕션 빌드 후 테스트 서버를 3030번 루프백 포트로 실행합니다. 검증용 고유 데이터만 생성·정리합니다.
브라우저 테스트는 추적·동영상·자동 스크린샷을 비활성화해 자격증명이 결과 파일에 남지 않도록 합니다.

스키마 변경 시 `npm run db:migrate -- --name 변경이름`으로 마이그레이션을 만듭니다.
비대화형 실행에서 경고로 막히는 경우 `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`로 SQL을 생성해 검토 후 마이그레이션으로 저장하고 `db:deploy`를 실행합니다.
배포·기존 마이그레이션 적용에는 `npm run db:deploy`를 사용합니다.

## 네트워크

패키지 설치 도메인과 `binaries.prisma.sh` HTTPS 접근이 필요합니다.
기존 403 차단은 환경 설정 게시 후 해소됐으며 체크섬·TLS 검증은 유지했습니다.

## 통합 입출금 장부

자금 관리 → 통합 입출금 장부에서 기간·은행·계좌·입출금·적요로 조회합니다.
합계와 계좌별 요약은 조회 조건 전체 기준이며 목록·출력은 현재 50건 페이지 기준입니다.
은행에서 받은 거래 후 잔액은 해당 계좌의 해당 거래 시점 금액으로 표시하고 계좌 간 누적 잔액을 만들지 않습니다.
순입출금은 기간의 입금−출금으로 현금 잔액이나 손익이 아닙니다.

엑셀은 5MB 이하 .xlsx, 첫 시트, 1회 최대 1,000건입니다.
기본 열은 거래일자·적요·입금액·출금액, 선택 열은 거래후잔액·거래시각입니다.
공통 양식을 내려받거나 인식 가능한 열 이름의 파일을 선택해 미리보기 후 계좌를 지정합니다.
동일 파일·계좌의 같은 행은 재등록하지 않습니다. 다른 파일의 동일 날짜·금액·적요는 확인을 요구합니다.
실제 은행별 원본 샘플은 아직 검증하지 않았으며 비밀번호 걸린 파일·.xls·모든 은행 변형 양식을 지원한다고 보장하지 않습니다.
장부의 실제 은행 거래를 예정·실적 화면에서 선택해 연결할 수 있습니다. 자동 추측 매칭은 하지 않습니다.

## 회계코드를 외우지 않는 거래 분류

건설업 계정과목 기본표 67개를 저장하고 거래 종류를 선택해 계정명·주의사항을 확인하도록 구성했습니다.
번호는 이 ERP의 내부 관리 번호입니다. [새 코드표](docs/ACCOUNTING-CHART.md)와 [기존 장부 검토](docs/EXISTING-LEDGER-REVIEW.md)를 참고하세요.
기존 계좌 코드를 거래에 상속하지 않습니다. 과태료·공과금·렌탈 종류 등을 구분하고 판단이 어려우면 미분류로 저장합니다.
'계정 수정'에서 실제 금액을 유지한 채 분류를 정정할 수 있습니다.
`npm run db:check-chart`는 임시 스키마에서 새 코드 전환과 기존 데이터 보관을 검증하고 정리합니다.

## 기존 연도별 엑셀 장부 이관 준비

자금 관리 → 기존 장부 가져오기에서 파일·시트를 선택하고 원장 은행 표기를 실제 계좌에 연결합니다.
250건씩 후보를 확인·선택한 후 미분류 상태로 가져옵니다. 날짜·금액·은행이 불확실한 행은 별도 검토 목록에 둡니다.
D·E 거래내용과 이전 구분·원본 시트/행을 보관하고, 원장 전체 잔액은 통장별 잔액으로 적용하지 않습니다.
실제 업로드 장부 분석 결과와 범위는 [장부 이관 검토](docs/LEGACY-LEDGER-IMPORT.md)를 참조하세요.

미분류 거래는 **자금 관리 → 미분류 묶음 정리**에서 검색하고 최대 100건씩 같은 용도로 분류할 수 있습니다. 선택 합계·적용 계정·사유를 확인한 후 저장하며, 최근 작업에서 적용 전 분류로 되돌릴 수 있습니다. 이후 개별 수정한 거래가 있으면 일괄 되돌리기를 중단합니다.

**공사 관리 → 현장별 지급 현황**에서 은행 출금을 여러 현장의 자재비·인건비·기타비로 나눠 기록하고 미배분 금액을 확인합니다. 본사·공통 지급은 별도로 구분합니다. [집계 기준 및 사용법](docs/PROJECT-PAYMENTS.md)을 참고하세요.

**공사 관리 → 현장별 지급예산**에서 자재비·인건비·기타비 지급예산을 입력하고 현장에 배분한 누적 지급액과 비교합니다. 항목별 초과, 미등록 예산과 변경 이력을 확인할 수 있습니다. [집계 기준 및 사용법](docs/PROJECT-BUDGETS.md)을 참고하세요.

**매입·매출 → 매입·매출 자료 / 미수·미지급 현황 / 부가세 추정**을 연결했습니다. 청구·증빙 등록 후 기존 은행 거래를 부분 연결하고 현장·거래처별 잔액을 확인할 수 있습니다. 부가세는 확인된 증빙과 공제 검토 상태를 기준으로 월별·분기별 추정합니다. [기준 및 범위](docs/TRADES-AND-RECONCILIATION.md).

**입출금 예정·실적**에서도 은행 거래를 연결해 실제 처리액과 남은 예정액을 갱신할 수 있습니다. 잘못 반영한 실적은 최근 처리부터 취소하면 자금 전망도 다시 계산합니다. [사용법](docs/CASH-BANK-CONNECTIONS.md).

## 회사 시험 사용 준비

[2026년 11월 2일(월) 시험 사용 안내](docs/MONDAY-PILOT.md)를 기준으로 준비합니다. `render.yaml`은 유료 웹 서버·운영 PostgreSQL 배포 구성 예시이며, 실제 계정 연결·요금 확인·코드 반영·배포가 필요합니다. 현재 인터넷 접속 주소는 아직 발급되지 않았습니다.

운영 전용 설정 검사는 `deploy:prepare`, 시작은 `start:cloud`, 상태 점검은 `/api/health`입니다. PostgreSQL 17 클라이언트가 있는 환경에서 `db:backup`, `db:restore`를 사용할 수 있으며 복구는 별도 빈 DB만 허용합니다. 자동 백업 예약은 서버 개설 후 별도로 설정해야 합니다.

**공사 관리 → 준공 예상 손익**에서 지급·미지급 매입과 추가 발생원가, 남은 예상 비용을 반영해 공사별 손익을 검토합니다. 현장 목록의 **손익계산서**를 누르면 해당 공사만 별도 조회·미리보기·인쇄·엑셀 저장할 수 있습니다. [계산 기준과 검토 절차](docs/PROJECT-PROFIT.md).

**자금 관리 → 발행어음대장**에서 회사 발행어음을 기록하고 발행일 기준 3개월 만기, 월별 만기 금액을 확인합니다. 기존 어음결제 예정에 연결하거나 확인 후 새 예정으로 만들며, 은행 전액 결제·실적 취소·등록 취소가 어음과 자금계획에 함께 반영됩니다. [사용법과 범위](docs/ISSUED-NOTES.md).

**자금 관리 → 수취어음·할인 관리**에서 보유 어음, 전액 추심, 할인료·실입금과 할인 후 만기 확인을 관리합니다. 기존 입금 예정을 재사용하고, 할인 시 순입금만 자금 전망에 반영합니다. 취소하면 어음·예정 상태를 복원합니다. [사용법과 범위](docs/RECEIVED-NOTES.md).

**자금 관리 → 송금 준비표 / 월세·공과금 정기 지급**에서 거래처 계좌와 다음 달 말일·즉시 지급 조건을 준비하고, 선택한 공사별 지급액을 계좌별 합산해 인쇄·엑셀 저장합니다. 송금 후 각 항목의 지급 내역 연결로 실제 지급을 반영합니다. [사용법](docs/TRANSFER-PREPARATION.md).

**인사·급여 → 직원·계약 단가 / 현장 출역·공수 / 월별 급여 검토**에서 일반·신호수 계약 일당과 여러 현장 공수를 직원별로 합산합니다. 사무실 월급제는 작업일보 없이 기준액을 별도로 관리합니다. [사용법과 계산 범위](docs/LABOR-AND-PAYROLL.md).

**인사·급여 → 급여 지급 확인**에서 직원별 최종 실지급액을 확인해 자금계획과 송금 준비표로 연결합니다. 확인 후 출역·계약 변경은 보류하며, 은행 실적을 연결하면 남은 금액을 갱신합니다. [확인·정정·지급 순서](docs/LABOR-AND-PAYROLL.md).

**차량 관리 → 차량·과태료 관리**에서 고정·공용 차량의 현장 사용, 보험·검사 기한, 유류비·정비비·과태료·범칙금과 회사·운전자 부담을 관리합니다. [사용법과 납부 확인 범위](docs/VEHICLES.md).

**자재·재고 관리**에서 품목·수량·단가, 현장 직납·회사 창고 이동·반납·사용을 추적합니다. [사용법](docs/INVENTORY.md).

**총원가 확인·공사 배부**에서 검토한 총 노무원가·회사 차량비를 공사별 손익에 연결합니다. [중복 방지·재검토 기준](docs/SOURCE-COSTS.md).

**법인세·지방소득세 추정 / 회계 전달·인수인계**에서 확인한 기준으로 전망을 남기고, 당시 자료의 전달본·전용 엑셀·전달 후 변경·마감을 관리합니다. [사용법](docs/FINANCE-DELIVERY.md).

**기준정보 → 증빙·원본 파일**에서 계약서·계산서·출역 사진·차량 고지서를 해당 업무에 첨부합니다. 회계 전달본은 엑셀과 당시 첨부 원본을 ZIP으로 내려받습니다. [첨부·백업 기준](docs/EVIDENCE-ATTACHMENTS.md).

**회사 통장 간 이체 / 송금 검토·구두승인**에서 출금·입금 쌍과 선택한 송금 내역의 구두승인 전달 기록을 관리합니다. [원본 보존·승인 기록 기준](docs/BANK-TRANSFERS-AND-APPROVALS.md).

개발 검증에는 Node.js 24, PostgreSQL 17, Chromium과 Python 3가 필요합니다. ZIP 상호운용 검증은 Python 기본 zipfile을 사용합니다. 테스트 명령은 실제 업무 자료가 없는 개발 DB에서 실행합니다.
